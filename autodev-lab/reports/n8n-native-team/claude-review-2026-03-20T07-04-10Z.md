## BLOQUEANTES (impiden produccion o paridad funcional)

### B1 — Cero cobertura de tests
**Severidad: Critica**
- No existe Jest, Vitest, ni `@testing-library/react-native` en `apps/mobile/package.json`
- El script `test:mobile` solo ejecuta `typecheck`, no tests reales
- No hay ningun archivo `.test.ts` / `.spec.ts` / `__tests__/` en `apps/mobile/`
- Sin regresion gate, cualquier cambio puede romper flujos sin que se detecte

### B2 — EAS profiles incompletos → builds de preview/prod fallan
**Severidad: Critica**
- `apps/mobile/eas.json`: ningun perfil declara `EXPO_PUBLIC_API_BASE_URL`
- `apps/mobile/app.config.ts` (lineas 40-53) lanza error si esa variable falta en preview/production
- `EXPO_PUBLIC_EAS_PROJECT_ID` esta **en blanco** en `.env.example` → push tokens y OTA updates rotos en Android
- Resultado: build de preview y produccion fallan antes de ejecutarse

### B3 — Push Notifications rotas en Android
**Severidad: Alta**
- `src/lib/pushNotifications.ts` linea ~103: depende de `EXPO_PUBLIC_EAS_PROJECT_ID`
- Variable vacia en `.env.example` y ausente en `eas.json`
- Tokens de Expo no se generan → notificaciones no funcionan en ninguna build distribuida

### B4 — Escalada de privilegios en Firestore
**Severidad: Alta (seguridad)**
- `firestore.rules` lineas ~152-161: el bloque `/users/{userId}` no restringe campos
  ```js
  allow update: if isAuthenticated() && request.auth.uid == userId;
  ```
- Cualquier usuario autenticado puede escribir `{ role: "boss" }` en su propio documento
- No existe validacion de campos permitidos (`request.resource.data.diff(resource.data).affectedKeys()`)

### B5 — Mismatch de colecciones en Firestore rules
**Severidad: Alta (seguridad + funcional)**
- Backend `marketplace.service.js` escribe en `/requests/{requestId}`
- `firestore.rules` cubre tanto `/requests/` como `/clientRequests/` pero con permisos asimetricos
- La regla sobre `/clientRequests/` deniega `create/update/delete`, pero el backend lo escribe directamente → operaciones del lado servidor pueden funcionar por Admin SDK, pero las reglas de seguridad client-side quedan inconsistentes con la realidad del schema

### B6 — Firebase keys hardcodeadas como fallback
**Severidad: Alta (seguridad)**
- `src/config/mobileEnv.ts` lineas 67-80: API key, App ID y credenciales Firebase visibles en el codigo fuente como fallback
- Esas credenciales van en el bundle publico de la app

### B7 — `apiService.ts` incompleto (4% de cobertura)
**Severidad: Media-Alta**
- `src/services/apiService.ts` (19 lineas) solo wrappea 3 funciones: `loadClientRequests`, `loadClientEmergencyCalls`, `loadEmployeeEmergencyCalls`
- `src/lib/api.ts` expone ~62 funciones; 25+ pantallas importan directamente de ese archivo
- La capa de abstraccion planificada no existe en la practica → no hay punto unico para retry, auth refresh, o error handling
