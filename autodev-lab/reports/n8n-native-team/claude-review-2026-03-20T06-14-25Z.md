### B3 — Mismatch de Firestore Rules: PERSISTE + NUEVO RIESGO
`firestore.rules` (raíz) vs `straight-wire-backend/firestore.rules`

Las reglas siguen divergentes en puntos críticos:

| Aspecto | Raíz | Backend |
|---|---|---|
| Colección principal | `/clientRequests/{id}` | `/requests/{requestId}` |
| Función `isClient()` | Definida | **Ausente** |
| Acceso empleados a usuarios | Todos leen todos | Solo propio uid o boss |
| `chatRateLimits` | Ausente | `allow read, write: if isAuthenticated()` |
| `OPEN_PRO_ESTIMATOR` en `validProAction()` | Presente | **Ausente** |

**Nuevo hallazgo en `straight-wire-backend/firestore.rules:129`:** La regla `/users/{userId}` permite `allow update: if isAuthenticated() && request.auth.uid == userId` sin restricción de campos. Cualquier usuario autenticado puede modificar su propio documento, incluyendo potencialmente el campo `role`. Si el backend no valida y restringe los campos actualizables, esto es un vector de escalamiento de privilegios.

### R2 — Firebase persistence: parcialmente mitigado, riesgo residual
`apps/mobile/src/config/firebase.native.ts` / `firebaseApp.ts`

El split `.native.ts` está bien estructurado: `firebaseApp.ts` inicializa la app base y `firebase.native.ts` agrega `AsyncStorage` persistence con try/catch para manejar re-inicializaciones. El riesgo residual es que Next.js o Vite (si el proyecto web importa desde `@/src/config/firebaseApp.ts`) ignorará el `.native.ts` correctamente, pero cualquier import directo desde `firebase.native.ts` en contexto web rompería silenciosamente.

---

### R3 — `mobileEnv.ts`: MEJORADO, riesgo residual en EAS
`apps/mobile/src/config/mobileEnv.ts`

La lógica de `getApiBaseUrl()` ahora está bien encapsulada con `console.warn` en builds de producción sin `EXPO_PUBLIC_API_BASE_URL`. Sin embargo, `eas.json` no define ningún bloque `env` con esta variable en los perfiles `preview` ni `production`. Un build EAS activará el warning pero usará el fallback localhost, haciendo inoperantes las llamadas de red en cualquier build distribuido.

```json
// eas.json — falta esto en los perfiles preview/production:
"env": { "EXPO_PUBLIC_API_BASE_URL": "https://tu-api.com" }
```

**Segundo hallazgo:** `mobileEnv.ts:46-58` tiene Firebase API keys hardcodeadas como fallback. Aunque las Firebase Web API keys son técnicamente públicas, su presencia en el código fuente facilita abuso si las reglas de Firestore tienen huecos (ver B3).

---

### R4 — Casts de navegación: CENTRALIZADO pero no eliminado
`apps/mobile/src/navigation/routes.ts:112`

Mejora real: el cast `as unknown as Href` está ahora en un único punto (`toExpoHref()`). Las pantallas usan `pushAppRoute()` y `replaceAppRoute()` en lugar de castear individualmente. Sin embargo, `toExpoHref` sigue siendo una supresión de error — si Expo Router cambia su tipo `Href`, el error seguirá silenciado. La solución correcta requiere habilitar `typedRoutes: true` en `app.json` y ajustar los tipos generados.
