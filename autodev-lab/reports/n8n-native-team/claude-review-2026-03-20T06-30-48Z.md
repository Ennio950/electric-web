## Estado del Repositorio — Post-Implementacion: `apps/mobile`

---

### BLOQUEANTES (impiden produccion o paridad funcional)

---

**B1 — Cero cobertura de tests**

No existe ningun framework de testing instalado. `package.json` no tiene Jest, Vitest, ni `@testing-library/react-native`. El script `test:mobile` solo ejecuta `typecheck`. Ningun archivo `*.test.*` o `*.spec.*` en toda la app.

- Impacto: imposible validar regresiones entre web y mobile, ni certificar flujos criticos (auth, marketplace, notificaciones).
- Archivo: `apps/mobile/package.json` — ausencia total de devDependencies de testing.

---

**B2 — `apiService.ts` al 4% — 77 funciones importan directamente de `src/lib/api.ts`**

`apps/mobile/src/services/apiService.ts` solo envuelve 3 funciones (`loadClientRequests`, `loadClientEmergencyCalls`, `loadEmployeeEmergencyCalls`). Los 25 archivos restantes importan directamente desde `src/lib/api.ts`, rompiendo la capa de servicio.

- Ademas existe `apiService.ts.autodev.bak` — artefacto del pase que no fue limpiado.
- Archivo: `apps/mobile/src/services/apiService.ts`

---

**B3 — Reglas de Firestore con mismatch de coleccion y vector de escalada de privilegios**

Dos problemas criticos coexisten:

1. La ruta en reglas del root usa `/clientRequests/{id}` pero el backend escribe en `/requests/{requestId}` — las reglas no cubren la coleccion real. Peticiones al marketplace quedan sin proteccion de lectura/escritura definida.
2. La regla de `/users/{userId}` permite actualizar cualquier campo sin restriccion de campos — un usuario autenticado puede escribir `role: "boss"` directamente en Firestore si el cliente la llama.

- Archivos afectados: `firestore.rules` (root) vs reglas en `straight-wire-backend`.

---

**B4 — Variables de entorno ausentes en perfiles EAS**

`eas.json` define tres perfiles (development, preview, production) pero ninguno declara `EXPO_PUBLIC_API_BASE_URL`. En `app.config.ts` hay validacion explicita que lanza error si no existe en preview/production. Un build de preview o produccion fallaría o caería al fallback de `127.0.0.1`.

- Archivo: `apps/mobile/eas.json`
- Archivo: `apps/mobile/src/config/mobileEnv.ts:46` — fallback a localhost activo

---

**B5 — `EXPO_PUBLIC_EAS_PROJECT_ID` vacio en `.env.example`**

`.env.example` tiene `EXPO_PUBLIC_EAS_PROJECT_ID=` en blanco. Sin este valor no se puede hacer OTA update ni build con EAS correctamente linkado al proyecto.

- Archivo: `apps/mobile/.env.example`

---

### OBSERVACIONES MENORES (no bloquean, pero afectan calidad y mantenibilidad)

---

**O1 — Pantallas sobredimensionadas**

| Archivo | Lineas |

| `app/(builder)/jobs/[id].tsx` | 707 |
| `app/(auth)/apply-employee.tsx` | 491 |

| `app/(client)/requests/[id].tsx` | ~465 |

No bloquean, pero dificultan testing unitario y mantenimiento. El builder jobs tiene logica de estimador, UI y estado mezclados.

---

**O2 — Casts de navegacion no eliminados**

`apps/mobile/src/navigation/routes.ts` centraliza `toExpoHref()` para suprimir los `as never`, pero el problema subyacente persiste: `typedRoutes: true` esta activado en `app.json` pero la generacion de tipos no cubre todos los paths dinamicos. Los casts son suppressores, no soluciones.

---

**O3 — Firebase API keys hardcodeadas como fallback en `mobileEnv.ts`**

`apps/mobile/src/config/mobileEnv.ts` tiene valores de Firebase como fallback si las variables de entorno no estan presentes. Si el `.env` no se configura correctamente, el app usa credenciales de produccion en desarrollo sin advertencia.

- Archivo: `apps/mobile/src/config/mobileEnv.ts`

---

**O4 — Hook unico en `src/hooks/`**

Solo existe `useMobileHomeQuery.ts`. La logica de data-fetching esta dispersa en 30 pantallas con `useQuery`/`useMutation` inline. Sin hooks por feature, cualquier cambio de API requiere edicion en multiples pantallas.

---

**O5 — Artefactos del pase sin limpiar**

- `apps/mobile/src/services/apiService.ts.autodev.bak`
- Posiblemente otros `.autodev.bak` en el repo.

---

**O6 — Notificaciones push: flujo Android no validado end-to-end**

`apps/mobile/src/lib/pushNotifications.ts:105` tiene una rama Android que genera token con `projectId` desde `Constants.expoConfig`. Si `EXPO_PUBLIC_EAS_PROJECT_ID` esta vacio (ver B5), el token no se genera correctamente en Android.

---

**O7 — Sin CI/CD pipeline para mobile**

No hay GitHub Actions workflow para mobile. Sin pipeline: los builds EAS no se disparan automaticamente, no hay lint/typecheck en PR, y no hay gate de calidad antes de produccion.
