## Revision post-implementacion — Electric Web Copia (apps/mobile)

---

### BLOQUEANTES

**B1 — Cero tests en apps/mobile**
- El unico script de "test" es `tsc --noEmit` (typecheck).
- 30 pantallas, 80+ funciones de API, flujos de auth, ciclo de vida de push tokens: todo sin cobertura.
- No hay Jest, Vitest ni testing-library configurados.
- Ruta: `apps/mobile/package.json`
- **Riesgo:** regresiones invisibles; cualquier PR puede romper flujos criticos sin saberlo.

**B2 — 19 de 21 pantallas siguen importando `api.ts` directamente**
- El fix-report confirmo que solo 2 pantallas fueron corregidas automaticamente (ambas en `(client)/`).
- 19 pantallas restantes acceden a `src/lib/api.ts` sin hooks intermedios.
- Rutas: `app/(boss)/`, `app/(builder)/`, `app/(employee)/`, parte de `app/(client)/`
- **Riesgo:** imposible agregar caching uniforme, retry logic, o intercambiar cliente de API sin tocar cada pantalla.

**B3 — Drift en `firestore.rules`**
- Dos versiones del archivo en conflicto: `firestore.rules` (raiz) vs `straight-wire-backend/firestore.rules`.
- La app movil confia en estas reglas para filtrado de datos por rol.
- **Riesgo:** agujeros de seguridad silenciosos; queries que funcionan en dev pueden fallar o exponer datos en prod.

**B4 — Resolucion fragil del EAS Project ID**
- `pushNotifications.ts` busca el ID en 3 lugares distintos con fallbacks encadenados: `Constants.expoConfig?.extra.eas.projectId` → `Constants.easConfig?.projectId` → `EXPO_PUBLIC_EAS_PROJECT_ID`.
- No hay error explícito si ninguno resuelve.
- Ruta: `apps/mobile/src/lib/pushNotifications.ts`
- **Riesgo:** build de produccion puede silenciosamente no registrar push tokens.

---

### RIESGOS ALTOS (no bloqueantes pero urgentes)

**R1 — Sin CI/CD pipeline**
- No existe `.github/workflows/` ni ninguna configuracion de CI.
- `eas.json` esta configurado pero no integrado con ninguna pipeline automatica.
- **Consecuencia:** ningun gate de calidad antes de publicar builds.

**R2 — Pantallas duplicadas entre grupos de rol**
- Logica identica o casi identica en:
  - `(client)/requests/`, `(employee)/requests/` → mismo concepto, codigo separado
  - `(client)/emergency/`, `(employee)/emergency/` → idem
- Ruta: `apps/mobile/app/(client)/` y `apps/mobile/app/(employee)/`
- **Riesgo:** bug corregido en un grupo no se propaga al otro.

**R3 — Type casts `as never` en navegacion**
- 6 ocurrencias en `(client)/`, 5 en `(builder)/`.
- Indica que Expo Router typed routes no esta resolviendo correctamente los tipos de navegacion.
- **Riesgo:** navegacion silenciosamente incorrecta; errores de runtime que TypeScript no atrapa.

**R4 — Pantallas sobredimensionadas**
- `app/(builder)/jobs/[id].tsx`: 707 lineas
- `app/(boss)/settings/index.tsx`: 404 lineas
- Mezclan `useMutation`, `useQuery`, `useState`, `useEffect` sin separacion clara.
- **Riesgo:** imposibles de testear unitariamente; alta probabilidad de bugs de estado.

**R5 — Sin metro.config.js ni babel.config.js**
- Usando defaults de Expo sin personalizacion.
- No hay configuracion de aliases, tree-shaking customizado ni soporte para monorepo paths explicito.
- **Riesgo:** si los packages `@electric/*` tienen imports internos no triviales, el bundler puede fallar en builds de produccion.

---

### OBSERVACIONES MENORES

**O1 — Sin extensiones `.native.ts` / `.web.ts`**
- Todo el branching de plataforma es inline via `Platform.OS`.
- El bundle web incluye codigo nativo (aunque no se ejecute).
- Aceptable por ahora pero aumenta el tamaño del bundle web.

**O2 — Firebase persistence hardcodeada para RN**
- `config/firebase.ts` usa `getReactNativePersistence(AsyncStorage)` sin abstraccion.
- Si se necesita web export del mismo app, esto falla.
- Ruta: `apps/mobile/src/config/firebase.ts`

**O3 — `imageUpload.ts` usa fetch propio, no el cliente principal**
- Ruta: `apps/mobile/src/lib/imageUpload.ts`
- No hereda headers de auth del cliente central. Dependiendo de como el backend valida uploads, puede ser un gap de seguridad menor.

**O4 — Permisos de location en español hardcodeados en `app.json`**
- `"NSLocationWhenInUseUsageDescription"` esta en español, lo que implica la app solo soporta un idioma.
- Si se internacionaliza después, este string no se actualiza dinamicamente.

**O5 — `dist/` comiteado**
- Output de build web (`apps/mobile/dist/`) esta en el repo.
- Ensucia el historial y puede causar confusion sobre que es fuente vs artefacto.
